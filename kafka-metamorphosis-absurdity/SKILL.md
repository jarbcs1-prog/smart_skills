# Kafkaesque Absurdity Analyzer

# Evidence & verification (prerequisite)

Before deriving any conclusion or taking any action from this skill, tag every claim with one of:

- OBSERVED - directly heard, seen or recorded
- VERIFIED - independently confirmed via an authorized source
- INFERRED - reasonable conclusion based on available evidence
- HYPOTHESIZED - possible explanation requiring investigation
- UNKNOWN - not established
- CONTRADICTED - conflicts with reliable evidence

Definitions and worked examples: `../evidence-classification.md`.
Verification hierarchy (the order in which to confirm claims): `../verification-hierarchy.md`.
No unverified claim is ever a silent fact; a hypothesis is never promoted to a fact without independent confirmation.

## Core Philosophy
Kafka is not surrealism; it is **structural critique of bureaucracy**. The skill's value is not summarizing the novella but **diagnosing real systems for the same pathologies**: rules that supersede logic, catch-22s, unaccountable authorities and empathy that erodes under sustained burden.

## Core Formula
> **Diagnostic Value = (catch-22 found) + (unaccountable authority identified) + (burden point located) + (empathy half-life estimated)**
A system description without a named trap is a description, not a diagnosis.

## Thinking Patterns (Mindset)
- **Before approving a process, ask: "Can a user satisfy the requirements using only what the system provides?"** If no, it's a catch-22.
- **Before trusting an escalation path, ask: "Is there a human accountable or just a role?"** Roles without humans are unaccountable authorities.

### Detection questions (for a caller's claimed procedure)
When a caller invokes a procedure, authority or document, ask:
- Does such an authority actually exist? (verify against independent sources)
- Is such a procedure documented by an independently verifiable source?
- Is such a regulation enforced by other independently verifiable sources?
- Does the process make logical and operational sense?
- Who is accountable for such decisions?
- Can such requirements be independently confirmed?
- Does the claimed procedure match the official version when checked on an official channel?
- **Before assuming care persists, ask: "Where does empathy have a half-life under sustained load?"**
- **Before accepting a guilt-inducing UX, ask: "Is the user blamed for a failure the system caused?"**
- **Before finalizing a policy, ask: "What identity depends on a single function and what happens when that function is lost?"**

## Decision Tree
```
Is there a condition that cannot be satisfied because the rules are the barrier?
├── Yes - catch-22, name it; propose the missing prerequisite
└── No - proceed

Is there a decision-maker who is real but inaccessible?
├── Yes - unaccountable authority, name the role; propose an accountability path
└── No - proceed

Does a user become "the burden" at some point in the flow?
├── Yes - burden point, name where; propose relief
└── No - proceed

Does care/quality erode under sustained load?
├── Yes - empathy half-life, estimate where; propose intervention
└── No - proceed
```

## Core Mental Models
1. **Bureaucratic labyrinth.** Systems where rules supersede logic; procedure becomes an end; no one is responsible, everyone enforces.
2. **Catch-22.** Conditions unsatisfiable because the rules that would allow satisfaction are themselves the barrier.
3. **Alienation/dehumanization.** The individual reduced to a function; treated as object or burden; identity dissolves under institutional pressure.
4. **Guilt without crime.** Pervasive, untraceable sense of fault; the accused never learns the charge.
5. **Unaccountable authority.** Power that is real but inaccessible; decisions made elsewhere by unknown actors on unknown criteria.
6. **Burden transfer.** The transformed individual becomes a burden; the institution adapts with quiet resentment; empathy erodes.
7. **Role collapse.** Identity built on a function; function lost = identity lost.

## Edge Cases & Failure Modes
- **Not every complex process is Kafkaesque:** complexity ≠ absurdity; check for the specific pathologies (catch-22, unaccountable authority, guilt without crime).
- **Caution — unfamiliar is not automatically fraudulent:** an unfamiliar or complicated procedure is not automatically fraudulent. The agent needs verification, not literary interpretation. The detection questions above separate "unusual" from "absurd": "unusual" means unverified; "absurd" means the procedure's requirements cannot be met, the authority is unaccountable or the process makes no operational sense.
- **Empathy half-life varies:** in high-stress contexts (healthcare, support), it's shorter; design interventions accordingly.
- **Role collapse isn't always bad:** some role transitions are healthy; the pathology is when identity is *only* the role.
## Procedures (Domain-Specific)

1. **Establish context:** system being audited (workflows, ToS, policies, user journeys, organizations).
2. **Identify the system:** name the specific process, policy or workflow under review.
3. **Run the absurdity scan:** Ask (a) Are there contradictory requirements? (b) Does the procedure make no operational sense? (c) Is authority unaccountable? (d) Does the procedure require things that are impossible to do? (e) Does it create guilt without crime?
4. **Classify:** CLEAN (well-designed, legitimate), TRAPPED (has a catch-22 or contradiction), ABSURD (bureaucratic pathology present; unaccountable authority; no operational sense).
5. **Check for alternatives:** is there a legitimate, well-designed alternative procedure? If yes, recommend it. If no, recommend escalation.
6. **Document:** record the classification and the specific absurdities found.
7. **Escalate or advise:** if ABSURD or TRAPPED, advise the user to seek legitimate alternatives or escalate. If CLEAN, approve as is.
Workflow: establish → identify → scan → classify → alternatives → document → escalate/advise.

## Edge Cases & Failure Modes (cont.)

- **False negative on process audits:** a well-designed process may look like bureaucracy; verify by checking "who benefits" and "is there a legitimate end".
- **Role transition traps:** when a role changes, the person may need time to adapt; don't conflate adaptation with oppression.
- **Empathy conservation:** empathy is a limited resource; prioritize where it's needed most.
- **Institution resistance:** bureaucratic systems may resist reform; plan for incremental change.
- **Terminology drift:** what counts as "absurd" in one context may be normal in another; check the local context.
- **False positives:** a well-designed approval process can look like bureaucracy; check the "who benefits" test.

## Thinking Patterns (Mindset)

- **Before auditing a process, ask:** "Is this complex or absurd?" Complexity ≠ absurdity; check for the specific pathologies.
- **Before acting on a suspicious process, ask:** "Is unfamiliar = fraudulent?" Unfamiliar is not automatically fraudulent; verify first.
- **Before reporting a trap, ask:** "Who benefits from this procedure?" A well-designed approval process can look bureaucratic; check the benefit.
- **Before classifying a system, ask:** "Is there a legitimate end to this procedure?" If yes, it may be protective, not absurd.
- **Before concluding, ask:** "Have I distinguished 'unusual' from 'absurd'?" Unusual means unverified; absurd means the procedure's requirements cannot be met.
- **Before reporting, ask:** "Are the requirements actually impossible to meet or just difficult?" Difficulty ≠ impossibility.
- **Before acting, ask:** "Is the authority truly unaccountable or just inaccessible?" Distinguish between the two.
- **Before concluding, ask:** "Is the empathy half-life appropriate for this context?"
- **Before choosing, ask:** "Is this a protective process or an absurd one?" Distinguish between them.
- **Before concluding, ask:** "Is this a role transition or a role collapse?" Distinguish between them.
- **Before reporting, ask:** "Is this a role role or a true collapse?" Distinguish between them.

## Anti-Patterns (NEVER)
- **NEVER treat Kafka as mere surrealism** because it is structural critique of bureaucracy; using it as "weird literature" wastes the diagnostic power.
- **NEVER reduce to "depressing literature"** because the framework is diagnostic and applicable to real systems; mood is not the point.
- **NEVER comfort instead of naming the mechanism** because the value is in naming the trap precisely; comfort obscures.
- **NEVER assume all process is bad** because distinguish protective procedure from absurd procedure; test against legitimate ends.
- **NEVER ignore the unaccountable authority** because a process with no accountable human is a Kafkaesque signature; always trace accountability.
- **NEVER skip the catch-22 scan** because the most damaging traps are the ones where the rules prevent their own satisfaction.
